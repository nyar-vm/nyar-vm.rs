# Nyar VM Maintenance Guide

This guide is intended for **internal maintainers and the core development team** of the Nyar VM project. It introduces the project architecture, module responsibilities, internal maintenance processes, and system-level design decisions.

> **Target Audience**: Project maintainers, core development team members, system architects
> **Content Focus**: Internal architecture, maintenance processes, system design, code organization

## Project Architecture Overview

Nyar uses a Rust Monorepo (Workspace) architecture, where each component is encapsulated in an independent crate, providing clear dependency relationships, independent testing environments, and efficient parallel compilation.

```
nyar-vm/
├── Cargo.toml         # Workspace root configuration
└── projects/
    ├── nyar-types/    # Unified intermediate representation type definitions
    ├── nyar-aot/      # AOT compiler and optimizer based on Chomsky
    ├── nyar-vm/       # Bytecode interpreter and VM execution core
    ├── nyar-jit/      # JIT compiler (Experimental)
    └── nyar-tools/    # Command-line tool (Nyar toolchain entry point)
```

External Dependencies:
- `ProjectChomsky`: Compiler backend optimization framework, located in `../ProjectChomsky`

## Core Design Philosophy

The architecture of Nyar is based on five design pillars:

### 1. 5-Stage Pipeline

A compiler is a process of performing a series of meaning-preserving transformations on program information, modeled as a pipeline of several carefully designed intermediate representations:

#### Stage 1: AST (Abstract Syntax Tree)
- **Responsibility**: Faithfully represent the syntax structure of the source code, preserving complete original information (such as SourceSpan) for diagnostics.
- **Implementation**: Provided by the frontend (e.g., `oak-rust`).
- **Key Processing**:
  - **Macro Expansion**: Executes macros and annotations, generating new AST nodes.
- **Optimization**: 
  - Very early constant folding (e.g., literal concatenation).
  - Syntax desugaring.

#### Stage 2: HIR (High-level IR)
- **Responsibility**: Global semantic graph, containing complete type information, scopes, and name resolution results.
- **Key Processing**:
  - **Symbol Resolution**: 
    - Handles imports, building cross-module symbol references.
    - Establishes namespace hierarchy, managing variable scopes and shadowing.
  - **Type Checking & Inference**: Ensures type safety.
  - **Pattern Matching Desugaring**: 
    - Converts complex `match` structures into decision trees.
  - **Algebraic Effect Desugaring**: Maps `try/handle` structures to underlying control flow primitives.

#### Stage 3: CFG (Control Flow Graph)
- **Responsibility**: Represents program execution logic in the form of BasicBlocks, making control flow explicit.
- **Key Processing**:
  - **Control Flow Linearization**: Converts structured control flow (if/while/loop) into Goto and SwitchInt.
  - **Desugaring Complex Control Flow**: 
    - Expands decision trees generated by pattern matching into a series of basic blocks and conditional jumps.
    - Maps algebraic effect `yield`/`resume` to explicit state saving and recovery.

#### Stage 4: SSA (Static Single Assignment)
- **Responsibility**: Variable versioning, ensuring each variable is assigned only once, handling control flow convergence via Phi nodes.
- **Key Processing**:
  - **Dominance Analysis**: Computes the dominator tree and dominance frontier.
  - **Phi Node Insertion**: Inserts Phi functions at the dominance frontier to handle variable merging.
- **Optimization (via nyar-aot)**:
  - **Global Value Numbering (GVN)**: Identifies and eliminates computationally equivalent redundant expressions.
  - **Sparse Conditional Constant Propagation (SCCP)**.
  - **Loop Invariant Code Motion (LICM)**.

#### Stage 5: LIR (Low-level IR)
- **Responsibility**: A linear instruction set close to the target machine.
- **Key Processing**:
  - **SSA Destruction**: Eliminates Phi nodes via mapping to stack slots or local variables.
  - **Instruction Selection**: Chooses optimal instructions based on the target platform (e.g., Nyar bytecode).
- **Dual Role**:
  - **Compilation Target**: Serves as an intermediate representation for generating external targets like WebAssembly.
  - **VM Target**: `NyarVM` acts as a reference interpreter, directly running the LIR instruction set.
- **Design Decision**:
  - **Stack Machine**: Nyar LIR uses a stack-based model for simplicity, compactness, and easy generation.

## Core Module Details

### nyar-types: Intermediate Representation Type Definitions
**Responsibility**: Centrally manages intermediate representation type definitions for each stage.

### nyar-aot: AOT Compiler and Optimizer
**Responsibility**: Implements transformations (passes) between stages and final bytecode generation.

### nyar-vm: VM and Interpreter
**Responsibility**: Implements the stack-based bytecode interpreter and runtime.

### nyar-tools: Command-line Tools
**Responsibility**: Provides command-line entry points for running and compiling Nyar programs.
